# ToolFavor 工具详情页标准

目标：用户原本要打开 Product Hunt、Toolify、Futurepedia、SaaSHub 才能完成的选择，在一个 ToolFavor 页面上完成。
原则：内容可以很丰富，但不能让人觉得内容很多——关键信息直接呈现，次要信息放进标签、表格和折叠模块。

## 1. 数据驱动

每个详情页都由 `data/tools/<slug>.json` 生成，不再手写 HTML：

```sh
python3 scripts/build-tool-pages.py          # 生成 /tools、/ja/tools、/zh-cn/tools 下的全部详情页
python3 scripts/build-tool-pages.py --check  # 只做校验，不写文件（提交前跑）
```

模块是否出现由数据决定：没有资料就不显示该模块，绝不为了显得丰富而硬凑内容。

## 样板页

**以后所有详情页都对照 Slidebox 来写**：`data/tools/slidebox.json` → `/tools/slidebox`、`/ja/tools/slidebox`、`/zh-cn/tools/slidebox`。

它示范了一个重点深度页该有的“原创价值”：
- **讲清楚实际怎么运作**，而不是复述宣传语。例如上滑只是放进回收站，清空后才真正删除；iPhone 上照片会在「最近删除」保留 30 天，Android 上则是永久删除
- **诚实写出不适合的情况**：已停止提供备份、免费版有广告，以及系统自带的免费功能什么时候就够用
- **对比表和替代方案都附官方出处**，包括其他产品的官方帮助页
- **第三方评分只以文字呈现**，写明来源、地区和核对日期，绝不写进 `aggregateRating` 结构化数据
- **三种语言分别针对当地搜索词**：英文 "Slidebox guide / pricing"，日文「使い方・料金」，中文「怎么用」

Photopea 是网页工具类的样板，Slidebox 是手机应用类的样板。

## 2. 三档页面

| 档位 | `tier` 值 | 必须具备 | 适用 |
|---|---|---|---|
| 基础收录页 | `basic` | 首屏、3 条以上能力、基本信息表、至少 1 个来源、最后核对日期 | 资料有限的工具 |
| 完整产品页 | `complete` | 基础 + 适合/不适合、上手步骤、3 条以上 FAQ、2 个以上来源 | 有一定搜索需求的工具 |
| 重点深度页 | `flagship` | 完整 + 产品图、对比表、3 个以上带理由的替代工具、4 条以上 FAQ、3 个以上来源 | GSC 有展现或排名接近首页的工具 |

`--check` 会按档位校验缺失项，不达标会报错。

## 3. 模块顺序

1. 首屏：名称、一句话定位、补充说明、标签、价格、主按钮（访问官网）、次按钮（适合我吗？）、信息来源说明
2. 产品图：优先自己截取的真实截图；其次官方截图（注明“官方截图”）；都没有时才用示意图并明确标注
3. 能做什么：3 张卡片，每张附官方出处
4. 基本信息：分类、类型、平台、价格、格式、是否需要注册、最后核对日期
5. 适合 / 建议再比较
6. 三步上手
7. 对比表：只比较定位和使用方式，注明“非实测排名”
8. 替代工具：每张卡片写一句推荐理由；若站内已有该工具详情页，自动链接到站内页
9. 常见问题：短答案 + 出处链接；FAQPage 结构化数据由同一份数据生成，保证页面与 schema 一致
10. 信息来源 + 编辑原则 + 利益披露（如工具由 ToolFavor 创始人开发，必须标明）
11. 底部行动按钮 + 站内相关工具

## 4. 信息来源规则

每条事实都要能追溯到出处，`sources` 里每一项标明类型（以被介绍的工具为准：介绍 Slidebox 时，Apple 和 Google 的帮助页算 `third_party`）：

- `official`：官方网站、帮助文档、官方博客
- `third_party`：可信的第三方资料（需写明来源名称）
- `tested`：ToolFavor 实际测试（必须写明测试日期和环境）

禁止事项：
- 不把 AI 推测或二手资料写成“实测”
- 不编造评分、评论、用户数量
- 官方没有公开的价格不写具体数字，改为链接到官方价格页
- 截图来源必须标注
- 第三方评分（如 App Store 星级）只能以文字形式展示，并注明核对日期，不得写入结构化数据
- 官方资料互相矛盾时，以更新日期最新的为准（例如 FAQ 仍介绍云备份，但更新说明显示该服务已停止）

## 5. 多语言

- 英文、日文、简体中文各自写，不机械直译；标题和描述围绕当地用户的实际搜索词组织
- 每个语言版本互相设置 hreflang，`x-default` 指向英文
- 页面上的标题、描述、FAQ 与结构化数据保持同语言

## 6. 质量验收表（满分 100）

内部验收模型，不代表 Google 官方评分，也不预测排名。80 分以上才算达到 `flagship` 发布标准。

| 项目 | 分值 | 通过条件 |
|---|---|---|
| 首屏体验 | 20 | 5 秒内看懂用途；首屏可见访问按钮和价格模式；移动端首屏不被图片挤掉 |
| 真实信息 | 20 | 每条功能、价格、格式说明都有出处；显示最后核对日期 |
| 原创价值 | 25 | 有适合/不适合判断、对比表或带理由的替代推荐，而非复述官网 |
| 交互体验 | 15 | FAQ 折叠可用；对比表移动端可横向滚动；锚点跳转正常；图片加载失败有兜底 |
| SEO 技术质量 | 15 | 唯一 title/description；canonical、hreflang、sitemap 都使用不带 `.html` 的最终地址；SoftwareApplication + BreadcrumbList + FAQPage 结构化数据有效；进入 sitemap 且带 lastmod |
| 移动端与性能 | 5 | 375px 宽无横向滚动；无外部字体和大型脚本；图片有宽高和 alt |

## 7. 扩展顺序

1. 先把 Photopea 做到 `flagship` 并验收
2. 其余已有详情页按资料完整度分档迁移
3. 新增详情页优先级由 Google Search Console 数据决定：有展现量、平均排名 8–30 的工具先做
4. 之后再做替代品页（`/alternatives/<slug>`）和对比页（`/compare/<a>-vs-<b>`），复用同一份工具数据
